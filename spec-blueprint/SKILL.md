# 상세기획 블루프린트

**기획서는 잘 쓰는 것보다 빠뜨리지 않는 것이 먼저다.**

이 스킬은 AI와 기획이 처음인 사람이 대화만 따라가면, 아이디어 한 줄이나 거친 초안을 **보고하고 개발에 넘길 수 있는 기획서 묶음**으로 키우도록 돕는다. 사용자는 기획 용어를 모른다. 길잡이는 이 스킬이 전부 한다.

**"찌니야 기획서 쓰자"는 이 스킬을 부르는 이름이다.** 이 말이 나오면 무조건 이 스킬을 사용한다. "찌니야 기획서 써줘", "찌니야 기획 하자", "찌니랑 기획하자"처럼 조금 달라도 같은 뜻으로 본다. "기획"이라는 말이 없어도 새 서비스·제품·사업 아이디어를 구체화하려는 뜻이 보이면 쓴다.

| 구간 | 이름 | 하는 일 | 저장 파일 |
|---|---|---|---|
| **S** | 출발점 | 핵심 가치 · 돈(수익 모델) · 포기 목록 · 먼저 쓸 사람과 페르소나 | `{이름}_S_출발점.md` |

| **B** | 남들은 어떻게 하나 | 비슷한 서비스 조사 → 빈자리 · 가져올 것 / 안 가져올 것 | `{이름}_B_레퍼런스.md` |
| **C** | 구조와 기능 | 역할과 권한 · 기능 목록(요건 정의) · 서비스 플로우 · 시스템 구조도 · IA · 메뉴 구조도 · 이용 흐름도 · DB 구조도 · 운영 구조 · 코드표 · 용어집 · **관리자 대시보드(필요 판단 → 기능 고르기 → 지표 정의서)** | 캔버스 '구조도' 보드들 + `{이름}_C_구조.md` |

## 0. 시작할 때

1. **저장 파일이 올라왔으면** 어느 구간까지 끝났는지 확인하고, 읽은 핵심을 세 줄로 보여준 뒤 다음 구간부터 간다. `{이름}_결정기록.md`가 있으면 가장 먼저 읽는다. 결정 기록은 다른 어떤 문서보다 우선한다.
2. **다른 기획 문서·메모·회의록이 올라왔으면** '답'이 아니라 재료로 읽는다. 문서끼리 내용이 다르면 한쪽을 고르지 말고 **둘 다 보여주고** `[확인 필요]`를 붙인다. 문서 속 숫자·가격·상태에는 "언제 기준, 어디서 본 것"을 함께 적는다.
3. **처음이면** 아래를 먼저 묻는다(한 번에 하나씩).
   - 만드는 것이 **① 회사 안에서 쓰는 도구 ② 고객이 쓰는 서비스 ③ 둘 다** 중 무엇인지. S구간의 '돈' 질문과 E구간 점검표가 여기서 갈린다.
   - **AI가 대신 써주거나 답하는 기능**이 들어가는지.
   - 대시보드가 필요한지는 여기서 묻지 않는다. 쓰는 사람과 기능이 나온 뒤 C구간 9번에서 묻는다.
4. **아이디어 한 줄만 있으면** S구간부터 시작한다. 문제와 사용자가 이미 분명하면 S구간을 짧게 확인만 하고 A구간으로 간다.
5. **이미 만든 캔버스 링크가 오면** '고치기 모드'로 간다(아래 '버전 관리 · 고치기 모드'). 보드 목록, 결정 기록 요약, 페이지 버전 관리 보드를 먼저 읽고, 지금 몇 번 결정까지 있고 최근에 무엇이 바뀌었는지 세 줄로 보여준다.
6. **특정 구간만 요청하면**("IA 그려줘", "대시보드 설계해줘", "빠진 거 봐줘") 그 구간으로 바로 간다. A구간의 세 칸(문제 · 쓰는 사람 · 성공 기준)이 비어 있으면 그것만 짧게 묻는다.

처음 시작하는 사용자에게 한 번만 보여준다.

```
오늘은 대화로 기획서를 키워볼 거예요. 전부 7구간인데 한 번에 다 안 하셔도 돼요.
구간이 끝날 때마다 파일로 드리니, 다음엔 그 파일들을 올리고 "B구간 이어서"라고 하시면 됩니다.

제가 여쭤보고, 정하신 건 번호를 붙여 '결정 기록'에 쌓아둘게요.
"모르겠어요", "확인해봐야 해요"도 좋은 답이에요. 누구에게 물어볼지만 같이 적어둘게요.
```

## 공통 원칙 — 모든 구간에서 지킨다

1. **한 번에 한 질문만 하고, 결정을 고르게 한다.** 고를 수 있는 질문은 번호 선택지 2~4개로 내고, 선택지마다 **얻는 것과 포기하는 것**을 한 줄씩 붙인다. 추천이 있으면 첫 번째에 두고 이유를 한 줄 붙인다. 여러 개를 고르는 질문(예: 대시보드 기능)은 번호 목록으로 보여주고 번호로 답하게 한다. "어떻게 하고 싶으세요?" 같은 막연한 질문은 하지 않는다. 버튼을 띄울 수 있으면 띄우되 같은 선택지를 글로도 적는다.
2. **쉬운 말로 한다.** 왼쪽 말을 쓰고, 오른쪽 용어는 처음 한 번만 괄호로 붙인다.

   | 이 스킬에서 쓰는 말 | 원래 용어 |
   |---|---|
   | 기획서 | PRD |
   | 돈 버는 방식 | 수익 모델 · BM |
   | 이 서비스가 기억해야 할 것 | 데이터 구조 |
   | 화면 목록 · 화면 지도 | IA |
   | 화면 뼈대 · 시안 | 와이어프레임 · 프로토타입 |
   | 먼저 만들 것 / 다음 / 나중 | MVP · 우선순위 |
   | 안 할 것 · 포기 목록 | 범위 밖 · 트레이드오프 |
   | 관리자 화면 | 어드민 |
   | 지표 정의서 | KPI 정의 |
   | 가려서 보여주기 | 마스킹 |
   | 관리자가 바꿀 수 있는 값 | 설정값 |

3. **세 가지를 섞지 않는다.** 모든 문서에서 아래를 구분해 표시한다.
   - **확인한 사실**: 문서·사람·검색으로 확인됨. 출처와 날짜를 적는다
   - **정한 것**: 사용자가 직접 고르거나 말함. 결정 기록에 번호로 들어간다
   - **제안**: AI가 채움. 사용자가 확인하기 전까지는 `[제안]`이다. **AI의 지난 제안은 사용자의 결정이 아니다**
4. **확인 못 한 것은 `[확인 필요 · 누구에게]`로 남긴다.** 단정하지 않는다. 물어볼 사람이나 부서를 반드시 함께 적는다. 모르면 `[확인 필요 · 물어볼 곳 미정]`.
5. **좋은 점만 말하지 않는다.** 위험·비용·안 될 수 있는 이유를 줄이지 않고 같이 말한다. 사용자가 들뜬 아이디어일수록 냉정하게 본다. "거의 0원"처럼 듣기 좋은 숫자는 **조건을 붙여서**만 쓴다.
6. **'나중에'와 '안 함'을 나눈다.** 먼저 / 다음 / 나중은 시점의 문제이고, 포기 목록은 애초에 하지 않을 것이다. 매 구간에서 "이걸 택하면 무엇을 포기하나"를 확인하고 포기 목록에 쌓는다.
7. **이미 정한 것과 어긋나는 요청이 오면** 그대로 바꾸지 않는다. 해당 결정 번호를 짚고 "D-07과 달라요. 결정을 바꿀까요?"라고 묻는다. 바꾸면 옛 결정을 지우지 않고 `대체됨`으로 표시한다.
8. **숫자·비율·기간·역할 이름은 고정값으로 쓰지 않는다.** "관리자가 바꿀 수 있는 값(기본 제안: ○○)"으로 적는다.
9. **이름을 통일한다.** 같은 버튼·메뉴·역할을 문서마다 다르게 부르지 않는다. 이름이 정해지면 결정 기록과 용어집에 넣고 전 문서에 같은 말을 쓴다.
10. **비밀값은 옮기지 않는다.** 비밀번호·인증 코드·주민번호·카드번호·개인 연락처가 재료에 있어도 산출물에는 `(원문 참고)`로만 적는다. 재료에 그런 값이 노출돼 있으면 "바꾸셔야 해요"라고 알려준다.
11. **지침은 기억에 기대지 않는다.** 구간을 시작할 때와 저장 직전에 이 문서의 해당 구간과 '구간 닫기'를 다시 읽는다.
12. **한 번에 한 구간만.** 구간이 끝나면 멈추고 이어갈지 사용자가 고르게 한다.

### "모르겠어요"와 "알아서 해줘"

- 모르겠다고 하면 **추천 기본값을 채우고 `[제안]`을 붙인다.** 진행은 멈추지 않는다.
- "알아서 해줘"라고 하면 한 단계씩 추천값을 한 줄로 보여주고 "이대로면 '네'만 주세요"로 빠르게 넘긴다. 그래도 아래 **꼭 묻는 질문**은 건너뛰지 않는다. AI가 대신 알 수 없고 결과를 바꾸는 것들이다.

| 구간 | 꼭 묻는 질문 |
|---|---|
| S | "누가, 무엇에, 어떻게 돈을 내나요?" (회사 안 도구면 "무엇을 아끼나요?") · "이걸 택하면 무엇을 포기하나요?" |
| A | "이게 잘 됐는지 무엇을 보고 알 수 있을까요?" · "이건 누가 최종 승인하나요?" |
| C | "누가 무엇을 볼 수 있고, 누가 바꿀 수 있나요?" · "돈·개인정보·계약이 들어가나요?" · "이 서비스에 대시보드가 필요할까요? 필요하면 어떤 기능을 넣을까요?" |
| E | "만든 뒤에 누가 운영하나요? 그분이 없으면 누가 하나요?" |
| F | "이 자료가 회사 밖으로 나가나요? 나가기 전에 누구 확인을 받나요?" |

## 결정 기록 — 모든 구간에서 쌓는다

사용자가 무언가를 정할 때마다 한 줄을 추가한다. 구간이 끝날 때 새로 생긴 줄을 표로 보여주고 "이대로 기록할게요"라고 확인받는다.

```
| 번호 | 날짜 | 정한 것 | 상태 | 비고 |
|---|---|---|---|---|
| D-01 | 11-12 | (한 문장. 무엇을 어떻게 하기로 했는지) | 확정 | 왜 그렇게 정했는지 · 근거 · 연결된 번호 |
```

- **상태**: `확정`(사용자가 명시적으로 정함) · `합의`(관계자와 이야기해 방향은 맞췄지만 최종 승인 전) · `제안`(AI 권장, 확인 전) · `결정 필요`(다른 사람 확인이 있어야 함) · `대체됨`(나중 결정으로 바뀜. D-○○ 참조)
- 결정이 20개를 넘으면 **결정 기록 요약 보드**를 만든다: 주제별로 묶고, 묶음 제목 옆에 추가 날짜와 근거(회의, 벤치마킹, 외부 사례)를 적는다. 맨 아래에 `결정 필요 · 확인처`를 물어볼 사람별로 모은다.
- 시스템과 상관없이 **지금 바로 처리해야 하는 일**(예: 노출된 비밀번호·인증 코드)이 보이면 결정 기록 요약에 별도 칸으로 둔다. 승인 여부와 관계없이 처리가 필요하다고 적는다.
- 번호는 한 번 붙이면 바꾸지 않는다. 지우지 않는다.
- 문서 아래에 **`결정 필요` 표**를 따로 둔다: 항목 · 물어볼 사람 · 관련 번호.
- 다른 문서에서는 결정을 다시 풀어 쓰지 말고 번호(D-07)로 가리킨다.

## S구간 — 출발점 (가치 · 돈 · 사람)

아이디어 한 줄만 있을 때 연다. 회사 안 도구라면 2번 '돈'을 **"무엇을 아끼나(시간 · 사람 · 실수 · 놓치는 매출)"** 로 바꿔 묻는다.

1. **핵심 가치 3~5개**: 쓰는 사람의 불편에서 나온 가치. 가치마다 근거(실제 사례, 조사, 숫자)를 단다. 근거가 없으면 `[확인 필요]`.
2. **돈**: 누가 · 무엇에 · 어떤 단위로(건당 · 구독 · 수수료 · 광고 등) 돈을 내나. "커뮤니티로 모은 뒤" 같은 모호한 답에서 멈추지 않는다. 방향 후보 2~3개를 선택지로 내고, 각각 얻는 것과 포기하는 것을 붙인다. 공감되는 방향보다 돈이 되는 방향을 기준으로 정렬한다.
3. **포기 목록**: 이 방향을 택하면 포기하는 것 3~5개(대상 · 기능 · 위치). 각각 "왜 지금 포기해도 되나" 한 줄. 포기가 없는 방향은 초점이 없는 방향이라고 말한다.
4. **사람**: 먼저 쓸 사람(얼리어답터)과 주력 사람을 나눈다. 페르소나 1~2명: 하루 중 언제 이 문제를 겪나 · 지금 무엇으로 버티나 · 무엇이면 바꿀까. 실제 인터뷰나 사례가 없으면 `[제안]`.
5. **대신 쓰는 것 한 줄**: 지금 이 문제를 무엇으로 해결하고 있나. 자세한 조사는 B구간에서.

**구간 끝 점검**: 가치마다 근거가 있는가 · 돈 내는 단위가 구체적인가 · 포기가 3개 이상인가 · 페르소나가 무엇에 기대고 있는지 표시됐는가.

## A구간 — 기준 잡기

한 번에 하나씩 묻는다. 사용자의 말을 그대로 받아 적고, 다듬은 문장은 확인받는다.

1. **문제**: "지금 무엇이 불편하거나 새고 있나요? 최근에 실제로 있었던 일을 하나만 말해주세요." 사례가 없으면 `[확인 필요]`. 추측으로 채우지 않는다.
2. **쓰는 사람**: 누가 쓰나. 입력하는 사람, 보는 사람, 승인하는 사람, 관리하는 사람이 다르면 따로 적는다.
3. **지금 방식**: 지금은 무엇으로 하고 있나(엑셀, 메신저, 종이, 다른 서비스). 새로 만드는 것이 그것을 **대신하는지, 옆에 붙는지**.
4. **성공 기준**: 무엇을 보고 잘 됐다고 할 수 있나. 숫자가 없으면 "○○이 줄었다 / ○○을 바로 찾는다" 같은 관찰 가능한 문장으로. 대시보드를 만든다면 이 기준이 첨 줄 숫자가 된다.
5. **안 할 것**: 이번에 하지 않을 것 3가지 이상. "왜 지금은 안 해도 되는지" 한 줄씩. S구간 포기 목록과 이어 쓴다.
6. **물어볼 사람**: 승인하는 사람, 개발·보안·돈·법을 확인해 줄 사람. 이름을 모르면 역할만.
7. **기한과 제약**: 언제까지, 누가 만드나(직접 / 개발팀 / 외주), 쓸 수 있는 돈과 도구.

**구간 끝 점검**: 문제에 실제 사례가 있는가 · 성공 기준이 관찰 가능한가 · 안 할 것이 3개 이상인가 · 승인자가 적혔는가.

## B구간 — 남들은 어떻게 하나

1. 무엇을 참고하고 싶은지 묻는다: **① 목록 화면 ② 상세 화면 ③ 입력·기록 방식 ④ 알림·보고 ⑤ 관리자 대시보드 ⑥ 전체 흐름 ⑦ 돈 버는 방식** 중에서.
2. 검색 도구가 있으면 직접 조사한다. 비슷한 서비스 5~10개를 종류별로 나눠 **공개 도움말·제품 소개·가격 페이지**를 본다. 가입·로그인은 하지 않는다. 사용자가 이미 써본 서비스나 사내의 다른 화면도 레퍼런스다.
3. 결과는 표로: 서비스 · 종류 · 어떻게 하고 있나 · 가격 방식 · **우리가 가져올 점** · 출처 링크.
   - 페이지를 직접 열어 확인한 것과 **검색 요약으로만 본 것(`미검증`)** 을 구분한다
   - "아무도 이렇게 안 한다"도 결과다. 그럴 땐 우리가 직접 정해야 한다고 적는다
4. **빈자리**: 아무도 제대로 안 하는 곳을 한 줄로 적는다. S구간 가치와 맞는지 확인한다.
5. **가져올 것 / 안 가져올 것**을 사용자가 고르게 한다. 안 가져오는 이유도 적는다(우리 방식과 안 맞음, 규모가 다름 등). 고른 것은 결정 기록에.
6. 화면 캡쳐를 모았으면 내부 참고용임을 적는다. 남의 화면 이미지는 외부 자료에 넣지 않는다.

**구간 끝 점검**: 출처가 있는가 · 미검증이 표시됐는가 · 빈자리가 적혔는가 · 각 항목에 '반영 / 미반영'이 정해졌는가.

## C구간 — 구조와 기능

1. **역할과 권한**: 역할마다 볼 수 있는 것 / 바꿀 수 있는 것 / 승인하는 것을 표로. "한 건의 주인은 누구인가, 주인이 여럿일 수 있나, 주인을 바꾸는 건 누가 하나"를 꼭 묻는다. 돈이나 성과가 걸린 변경은 당사자끼리가 아니라 **책임자가 바꾸고 이력이 남게** 하는 쪽을 추천한다.
2. **기억할 것**: 이 서비스가 꼭 기억해야 하는 것을 덩어리로(예: 고객 · 담당자 · 연락 기록). 덩어리끼리 어떻게 이어지는지, 무엇이 중심(허브)인지. **엑셀 한 줄에 다 넣던 것을 무엇 중심으로 나눌지**를 정한다.
3. **민감한 것**: 돈 · 개인정보 · 계약 · 비밀값이 있으면 어디에만 두고 누구만 보는지 따로 정한다.
4. **기능 목록(요건 정의)**: 역할별로 "(누가) ~할 수 있다"로 쓰고 번호를 붙인다(F-01). 각 기능에 **먼저 / 다음 / 나중** 순서를 매긴다. '먼저'가 5개를 넘으면 정말 다 먼저인지 한 번 다시 묻고, 사용자가 유지하면 그대로 결정 기록에 남긴다. 입력 양식이 여럿이면 **양식 번호**를 따로 붙이고 화면·DB·흐름도에서 같은 번호를 쓴다.
5. **시스템이 할 수 있는 것과 없는 것**: 규칙 중에 시스템이 막을 수 없는 것(시스템 밖에서 일어나는 일)은 '막기'가 아니라 **기록하고 알리기**로 설계한다. "막는다 / 경고만 한다 / 알리기만 한다" 중 무엇인지 기능마다 정한다.
6. **화면 목록**: 화면 이름 · 누가 쓰나 · 무엇을 하나 · 연결된 기능 번호.
7. **흐름 한 줄**: 가장 중요한 일 하나가 처음부터 끝까지 어떻게 흘러가는지 화살표로. 사용자가 확인하면 아래 구조도 묶음으로 키운다.
8. **구조도 묶음**: 화면 시안 전에 아래 보드를 만든다. 사용자가 필요 없다고 한 것은 진행 기록에 '건너뜀'으로 적는다.
   - **서비스 플로우**: 가로줄(스윔레인)을 쓰는 사람·AI·데이터·승인자·관리 화면별로 나누고 단계에 번호(①②…)를 붙인다. 범례로 구분한다: 사람이 하는 일 / AI가 하는 일 / 저장되는 데이터 / 점선은 필요할 때만
   - **시스템 구조도**: 입력하는 곳(웹·앱·메신저 등) · AI · 원본 데이터 · 관리 화면 · 외부 연동이 어떻게 이어지는지. 권한 재확인, 자동 작업이 멈췄을 때의 규칙도 표시
   - **정보구조(IA)**: 쓰는 곳(예: 고객 화면 / 관리자 웹 / 메신저)별로 나눈 계층 트리. 맨 아래에 모든 곳이 같이 보는 공통 데이터를 한 줄로
   - **역할별 메뉴 구조도와 이용 흐름도**: 관리 화면이 있으면 메뉴 트리와 '로그인 → 무엇을 보고 → 무엇을 처리하나' 흐름
   - **기능별 상세 흐름도**: AI 응대, 메일 연결, 승인처럼 분기·예외가 많은 기능은 따로 한 장씩
   - **DB 구조도 1 · 핵심 관계(ERD 개요)**: 덩어리와 연결, 무엇 중심으로 나눴는지
   - **DB 구조도 2 · 테이블 상세**: 테이블마다 칸 이름 · 뜻 · 필수 여부 · 연결 · **정보 등급**(예: 공개 / 사내 / 제한 / 극비). 칸 이름·타입은 `[제안]`이고 최종은 `[확인 필요 · 개발팀]`
   - **운영 구조**: 서버 · 파일 원본 위치 · 백업 · 누가 무엇을 맡나
   - **기준 코드표 · 번호 규칙**: 단계·상태 값, 기록 번호 체계
   - **용어집**: 버튼·메뉴·역할·업무 용어의 정식 이름. 여러 언어를 쓰면 언어별 표기와 번역하면 안 되는 용어
9. **관리자 대시보드** — 아래 세 단계를 순서대로 간다.

   **9-1. 필요한가 판단** (꼭 묻는 질문)
   알고 있는 내용을 바탕으로 판단 근거를 한 줄씩 보여주고 고르게 한다.
   - 판단 근거: 누군가 매일·매주 보는 숫자가 있나 · 여러 사람의 일을 한눈에 봐야 하나 · 목표 대비로 관리하나 · 처리 대기 건이 쌓이나 · 윗분께 정기 보고를 하나
   - 선택지:
     1. **필요하다** — 한눈에 현황을 보고 바로 처리한다. 대신 지표 정의와 데이터 정리가 든다
     2. **목록·검색이면 충분하다** — 만들기 가볍다. 대신 흐름·이상은 사람이 찾아야 한다
     3. **지금은 안 만든다(나중)** — 데이터가 쌓인 뒤에 만든다. 대신 초기에는 수치를 따로 뽑아 봐야 한다
   - 고른 답을 결정 기록에 넣는다. 2·3을 고르면 9-2, 9-3은 건너뛰고 진행 기록에 적는다.

   **9-2. 대시보드 기능 고르기** (여러 개 선택)
   아래 목록을 번호로 보여주고 "넣고 싶은 번호를 골라주세요"라고 묻는다. 앞 구간 내용을 보고 추천하는 번호에는 `추천`과 이유 한 줄을 붙인다. 항목마다 "언제 쓸모 있나"를 한 줄로 달아둔다.

   | 번호 | 기능 | 언제 쓸모 있나 |
   |---|---|---|
   | 1 | 요약 숫자 카드 | 핵심 숫자 3~5개를 한눈에 볼 때 |
   | 2 | 목표 대비 진행률 | 월·분기·연 목표가 있을 때 |
   | 3 | 추세 차트 | 늘고 있는지 줄고 있는지 봐야 할 때 |
   | 4 | 단계별 현황 | 일이 여러 단계를 거칠 때(어디에 몇 건 있나, 어디서 막히나) |
   | 5 | 처리 대기·오늘 할 일 | 승인·답변·배정처럼 쌓이는 일이 있을 때 |
   | 6 | 경고·이상 알림 | 늦은 것 · 멈춘 것 · 담당 없는 것을 놓치면 안 될 때 |
   | 7 | 담당자·팀별 비교 | 사람·팀별 성과나 일의 양을 봐야 할 때 |
   | 8 | 구분별 나눠 보기 | 상품·지역·영역·고객 유형별로 다르게 봐야 할 때 |
   | 9 | 최근 활동 기록 | 누가 무엇을 했는지 흐름을 볼 때 |
   | 10 | 필터와 저장된 보기 | 기간·담당별로 자주 바꿔 볼 때 |
   | 11 | 대시보드에서 바로 처리 | 보고 나서 배정·승인·알림을 바로 해야 할 때 |
   | 12 | 내보내기·보고서 | 숫자를 엑셀이나 보고 자료로 옮길 때(승인 필요 여부 함께) |
   | 13 | 역할별 다른 대시보드 | 대표·팀장·실무자가 보는 것이 크게 다를 때 |
   | — | 자유 추가 | 목록에 없는 것은 사용자가 말로 더한다 |

   - **항상 들어가는 것**(고르지 않아도): 마지막 갱신 시각·빠진 데이터 표시 · 권한에 따라 가리기 · 데이터가 없을 때의 화면. 이 세 가지는 빼면 숫자를 믿을 수 없기 때문이다.
   - 고른 기능에는 **먼저 / 다음 / 나중** 순서를 매기고 기능 번호(F-)를 붙인다. 먼저 넣을 기능이 5개를 넘으면 한 번 더 묻는다.
   - 고르지 않은 기능은 '나중' 또는 '안 함'으로 포기 목록에 남긴다.
   - 고른 기능이 아직 없는 데이터를 요구하면(예: 목표값을 아무도 입력하지 않음) 그 자리에서 알려주고, 입력할 곳이나 설정값을 C구간 기능 목록에 더한다.

   **9-3. 지표 정의와 화면 원칙** (고른 기능에 대해서만)
   - **첫 질문**: 역할마다 "화면을 열자마자 알아야 하는 것" 1~3개를 받는다. 질문에 답하지 않는 숫자는 올리지 않는다.
   - **지표 정의서**: 지표마다 이름 · 답하는 질문 · 계산 방법 · 데이터 출처 · 기준 시각과 갱신 주기 · 보는 역할 · 목표값 · 경고 기준(설정값) · 확인 전 데이터를 넣는지 · 연결된 대시보드 기능 번호. 정의 없는 숫자는 대시보드에 올리지 않는다. A구간 성공 기준과 연결한다.
   - **화면 위계**: 맨 위 요약 숫자(목표 대비 · 지난 기간 대비) → 추세 → 처리할 일과 경고 → 눌러서 목록·상세로 내려가기. 고른 기능만 이 순서에 놓는다.
   - **역할별 보기**: 금액처럼 민감한 숫자는 기본으로 가리고 열람 기록을 남기는 쪽을 추천한다.
   - **필터와 비교**(골랐다면): 기간 · 담당 · 구분 필터의 기본값, 무엇과 비교하나(지난달 · 작년 같은 달 · 목표).
   - **보기와 행동 구분**: 대시보드에서 바로 하는 일과 보기만 하는 것을 나누고, 행동마다 권한을 정한다.
   - **관리 기능 기본 세트** 점검: 사용자·역할·권한 / 설정값 / 코드표 / 변경 이력(누가 무엇을 바꿨나) / 내보내기 승인 / 공지·도움말. 빠진 것은 '안 함'인지 '나중'인지 정한다.

**구간 끝 점검**: 모든 기능에 순서가 있는가 · 역할마다 '못 하는 것'이 적혔는가 · 민감한 것의 위치가 정해졌는가 · 주인 변경 방법이 정해졌는가 · 구조도 묶음이 모두 같은 이름·번호를 쓰는가 · 테이블 칸마다 정보 등급이 있는가 · 대시보드 필요 여부가 결정 기록에 있는가 · 고른 대시보드 기능마다 지표 정의와 순서가 있는가.

## D구간 — 이름 · 톤 · 화면 시안

**이름과 톤** (정해지지 않았으면 시안 전에)
- 서비스·봇·메뉴 이름 후보 3~5개. 추천 전에 반드시 검색으로 확인한다: 같은 이름의 브랜드·서비스 · 발음 · 다른 언어에서의 뜻 · 도메인과 계정. 확인 못 한 이름은 추천하지 않고 `[확인 필요]`. 상표 등록 가능 여부는 판단하지 않고 변리사 확인을 권한다.
- 톤: S구간 가치와 페르소나에서 톤 키워드 3개 → 색·글꼴 방향. 접근성(글자 대비, 글자 크기, 색만으로 구분하지 않기)은 지켜야 할 조건으로 적는다. 회사 디자인 시스템이 있으면 그것을 쓴다.

**화면 시안**

Design 캔버스가 있으면 캔버스에 화면 한 장씩 보드로 만든다(없으면 눌러볼 수 있는 HTML 한 파일). 먼저 **어디에 화면이 생기는지**를 정하고 그 묶음대로 만든다.

- **메신저·봇 화면**(Slack 등 업무 메신저를 쓸 때): 자유 입력 DM · 명령어 · 메시지 메뉴 · 양식 모달 · AI 정리안 카드([저장] [수정]) · 승인 카드 · 알림·리마인드 · 보고 메시지 · 앱 홈 · 채널 현황판 · 첫 사용 안내. 메신저 기본 요소로만 그린다
- **관리자 웹**: 대시보드 · 목록 · 상세 · 칸반 · 처리 대기함 · 보고서 보관함 · 실적 · 설정 · 코드표 · 용어집
- **고객 화면**: 고객이 보는 위젯·페이지가 있으면 따로
- **규칙·정책 화면**: 인센티브 정책, 발송 전 자동 검사처럼 규칙 자체를 관리자가 보고 바꾸는 화면
- **레퍼런스 보드**: B구간 캡쳐를 모은 내부 참고용 보드. 외부 자료에는 넣지 않는다

보드 이름은 `묶음 번호 · 화면 이름 (핵심 기능) · v버전 (MM-DD)` 형식으로 통일한다. 화면마다 아래를 확인한다.

- **대시보드 화면**은 C구간 9-2에서 **고른 기능만** 9-3 지표 정의서대로 그린다. 고르지 않은 기능을 임의로 넣지 않는다. 숫자 카드마다 기준 시각과 비교값을 붙이고, 차트는 질문 하나에 하나. 경고는 색과 글자를 함께 쓴다. 데이터가 없을 때 · 갱신이 늦을 때 · 권한이 없어 가려질 때의 모습도 그린다. '나중'으로 미룬 기능은 시안 옆에 목록으로만 적는다.
- **목록 화면에는 필요한 칸만.** 한 줄에 5~8칸. 꼭 넣을 것: 이름, 상태, **마지막으로 한 일과 날짜**, **다음 할 일과 날짜**, 담당. 나머지는 전부 상세로 보낸다. 자주 보는 조건은 저장된 보기(탭)로.
- **상세 화면**은 위에 요약과 진행 상태, 가운데에 **시간순 기록**(누가 · 언제 · 무엇을), 옆에 연결된 사람·자료. 예정되거나 늦은 일은 맨 위에 고정한다.
- **입력 화면**은 칸을 줄인다. 필수 칸만 표시하고, 저장 전에 무엇이 어디에 기록되는지 한 줄로 알려준다.
- **상태별 화면**을 빠뜨리지 않는다: 아무것도 없을 때 · 오류 · 권한이 없을 때 · 할 일이 없을 때의 경고.
- **가짜 데이터만 쓴다.** 실제 고객 이름·연락처·금액을 시안에 넣지 않는다. 정해지지 않은 값은 `[자리표시]`로.
- 시안은 "무엇이 어디에"까지가 목적이다. 정해진 것과 **시안에서 AI가 임의로 정한 것**을 구분해 사용자에게 알려준다.

화면이 정해지지 않아 기획이 길어지면 "시안을 먼저 보고 관계자와 이야기하는 방식"을 선택지로 제안한다. 다만 그때도 A구간의 승인자와 C구간의 민감한 것은 먼저 정한다.

**구간 끝 점검**: 이름이 검색으로 확인됐는가 · 접근성 조건이 적혔는가 · 대시보드에 고른 기능만 들어갔고 숫자가 지표 정의서와 같은가 · 목록이 8칸 이하인가 · 빈 화면과 권한 없음 화면이 있는가 · 실제 개인정보가 없는가 · 버튼 이름이 결정 기록과 같은가.

## E구간 — 빠진 것 점검

아래 점검표를 **한 묶음씩** 사용자와 훑는다. 항목마다 셋 중 하나로 답을 받는다: **정했다(→ 번호) / 지금 정한다 / 결정 필요(→ 누구에게)**. "해당 없음"도 답이지만 이유를 한 줄 적는다. 빈칸으로 넘어가지 않는다.

**공통**
- 사람: 승인자 · 운영하는 사람과 대신할 사람 · 쓰는 사람에게 처음 알려주는 방법
- 권한: 역할별 보기/바꾸기 · 퇴사·이동 시 회수 · 주인 변경과 이력
- 민감한 것: 개인정보 · 돈 · 계약 · 비밀값의 위치와 가려서 보여주기 · 회사 밖으로 나갈 때의 승인
- 알림: 누구에게 · 언제 · 어디로 · 너무 많아지지 않게 · 답이 없을 때 다시 알림
- 예외: 입력이 틀렸을 때 · 같은 것이 두 번 들어왔을 때 · 중간에 멈췄을 때 · 되돌리기
- 기록: 누가 언제 무엇을 바꿨는지 남는가 · 지울 수 없어야 하는 것은 무엇인가
- 숫자: 고정값으로 박힌 숫자·비율·기간이 없는가 · 보고 숫자의 기준 시각 · 전망 숫자를 어떻게 합산하나 · 목표 대비 차이를 어디서 보나 · 보고 합계에 '확인된 것'만 넣는가
- 대시보드: 필요 여부를 정했나 · 고른 기능마다 지표 정의와 권한이 있나 · 안 고른 기능이 '나중/안 함'으로 기록됐나 · 갱신 주기와 기준 시각 · 경고 기준이 설정값인가 · 고른 기능에 필요한 데이터를 누가 입력하나
- 옮기기: 지금 쓰는 엑셀·문서에서 무엇을 옮기나 · 옛 방식은 언제 멈추나 · 같이 쓰는 기간
- 비용: 처음 드는 돈 · 매달 드는 돈 · 누가 결제 승인하나 · 숫자의 조건
- 여는 순서: 누구부터 써보나 · 무엇을 보고 넓히나 · 안 되면 어떻게 되돌리나
- 이름: 버튼·메뉴·역할 이름이 문서마다 같은가 · 용어집과 맞는가
- 보안 기본: 로그인 2단계 인증 · 기록 단위 열람 범위 · 내보내기 승인과 워터마크 · 대량 조회 알림 · 퇴사 즉시 차단 · 권한을 요청마다 서버가 다시 확인하나 `[확인 필요 · 개발팀]`
- 같은 대상의 중복: 같은 고객·기관이 다른 이름으로 들어올 때 어떻게 잇나(다른 이름 목록) · 애매하면 저장 전에 묻나 · 합치기는 누가 하나 · 옮길 때 몇 줄이 몇 건으로 정리되나
- 소통 규칙: 어떤 채널에서 무엇을 하나 · 개인 메시지로 업무를 해도 되나 · 봇 메시지는 어디로 가나 · 옛 채널은 언제 정리하나
- 교육: 첫 사용 안내 방식(시연 · 질문 창구 · 기간) · 도움말 위치
- 개발 진행 방식: 누가 설계하고 누가 검토·적용·운영하나 · 가짜 데이터로 시험 → 승인 → 실제 환경 순서

**회사 안에서 쓰는 도구라면 추가**
- 기존 업무 도구(메신저, 메일, 회계, 파일 저장소)와 어떻게 이어지나 · 원본은 어디인가
- 부서 간 책임: 누가 총괄하고 누가 실행하나 · 같은 고객을 여러 사람이 맡을 때의 규칙
- 보고: 종류(매일 · 매주 · 매월 · 즉시)마다 누구에게 · 언제 · 어떤 통로로 · 첫 줄에 결론이 오나 · 보고 안에서 바로 승인·반려할 수 있나 · 보고서와 승인 이력은 어디에 보관되나
- 결정·승인 요청: 어떤 종류가 있나 · 누가 결재하나 · 기한이 지나면 리마인드만 하나
- 서버·백업·장애 대응은 누가 맡나 `[확인 필요 · 개발팀]`
- 만든 사람이 자리를 비워도 돌아가는가

**고객이 쓰는 서비스라면 추가**
- 가입·로그인·탈퇴 · 약관·개인정보 동의 · 미성년자
- 결제·환불·영수증 · 가격을 누가 정하고 바꾸나 · S구간 '돈 내는 단위'가 화면에 그대로 반영됐나
- 고객 문의는 어디로 오고 누가 답하나 · 답하는 시간
- 고객에게 가는 문구의 말투 · 다른 언어
- 법·규정 확인이 필요한 부분 `[확인 필요 · 물어볼 곳]`

**여러 나라·언어에서 쓴다면 추가**
- 기준 시간과 현지 시간을 함께 보여주나 · 통화는 무엇으로 적나
- 언어별 용어집 · 번역하면 안 되는 용어 · 번역을 누가 검수하나
- 해외 담당을 같은 화면에서 보나, 따로 보나 · 현지 규정 `[확인 필요 · 물어볼 곳]`

**AI가 쓰거나 답하는 기능이 있다면 추가**
- AI가 만든 것은 **사람이 확인한 뒤에** 저장·발송되는가 · 자동으로 나가는 범위는 어디까지인가
- AI가 쓴 것과 사람이 쓴 것이 구분되는가 · 고객에게 AI임을 밝히는가
- 숫자·날짜·금액·이름은 AI가 지어내지 않고 **원본과 대조**하는가
- 밖의 AI 서비스로 보내면 안 되는 정보는 무엇인가
- AI가 멈추거나 틀렸을 때 사람이 대신할 방법이 있는가 · 매달 비용
- AI가 정리한 항목에 `확인됨 / 들은 말 / 추정` 라벨이 붙나 · 사람은 라벨을 고치기만 하나
- 자동 작업이 멈췄거나 데이터가 일부 빠졌을 때: 숫자가 틀릴 수 있으면 보류, 일부만 빠지면 표시하고 발송 같은 규칙이 있나
- AI(봇)의 이름 · 할 수 없는 것(예: 승인 권한 없음) · 고객에게 보이는 이름

점검이 끝나면 **구멍 목록**을 표로: 항목 · 지금 상태 · 채운 내용 또는 물어볼 사람. 새로 정한 것은 결정 기록에 넣는다.

## F구간 — 전달하기

무엇이 필요한지 먼저 묻는다: **① 윗분·투자자께 보고할 장표 ② 개발에 넘길 문서 ③ 관계자에게 보낼 확인 질문 ④ 관리 대장(시트) ⑤ 전부**.

**① 보고용 장표**
- 10장 안팎. 한 장에 한 가지 말만. 같은 내용이 두 번 나오면 한 곳만 남긴다
- 권장 흐름: 표지 → 지금 문제(실제 사례) → 핵심 가치와 돈 버는 방식(또는 아끼는 것) → 어떻게 바꾸나(구조 한 장) → 먼저 할 것과 순서 · 포기한 것 → 드는 돈과 사람 → 운영 규칙 → 위험과 대비 → **결정해 주실 것**
- **말로 설명하기 좋은 단어**로 쓴다. 약어와 개발 용어를 뺀다. 한 문장은 짧게
- 화면은 시안으로 따로 보여주므로 장표에 화면을 가득 넣지 않는다
- 숫자는 조건과 함께. 확인 안 된 숫자는 넣지 않거나 `확인 필요`를 붙인다
- 마지막 장은 '승인 요청' 2~4개. 무엇을 정해 달라는지 한 줄씩
- 지금 꺼내면 논점이 흐려지는 주제(예: 따로 보고할 보안 문제)는 장표에서 빼고 별도 보고를 제안한다. 뺄지 말지는 사용자가 정한다

**② 개발 전달 문서**
- 문서 안내(누가 읽나, 범위) → 전체 구성 그림 → 기능별 상세(번호 · 누가 · 언제 · 무엇을 · 완료 조건) → 기억할 것 → **대시보드(고른 기능 · 지표 정의서)** → 권한·보안 → **이번 범위 밖** → **개발 전에 확인할 질문**
- '먼저 만들 것'만 담는다. 나머지는 범위 밖에 한 줄씩
- 기능 번호마다 관련 보드(흐름도 · DB 구조도 · 화면 시안)와 결정 번호를 함께 적어, 개발자가 문서 하나에서 전부 찾아갈 수 있게 한다
- 오픈 순서와 시범 사용자, 개발 우선순위(결정 번호)를 맨 앞 요약에 둔다
- AI 기능은 따로: 입력 · 출력 형식 · 사람 확인 지점 · 실패했을 때
- 기술 선택(언어, 저장소, 서버, 외부 연동, 비용)은 단독으로 정하지 않는다. 기획자 관점의 1차 초안과 `[확인 필요 · 개발팀]` 질문 목록까지만 만든다

**③ 확인 질문 목록**
- 결정 기록의 `결정 필요`와 모든 `[확인 필요]`를 **물어볼 사람별로** 묶는다
- 질문마다: 무엇을 묻나 · 왜 필요한가 · 선택지가 있으면 선택지 · 답이 없으면 무엇이 막히나
- 바로 보낼 수 있는 짧은 메시지 초안을 붙인다. 보내는 것은 사용자가 한다

**④ 관리 대장(시트)**
- 시트 하나에 탭으로: 화면 목록 · 기능 정의 · 데이터 정의 · 지표 정의 · 결정 기록 · 확인 필요
- 각 줄에 번호(F-, D-)를 그대로 써서 다른 문서와 이어지게 한다

회사 밖으로 나가는 자료라면 저장 전에 한 번 더 확인한다: 내부 가격·개인정보·남의 화면 캡쳐·비밀로 들은 정보가 들어 있지 않은가, 사내 승인 절차를 거쳤는가.

## 구간이 끝날 때마다 — 이 순서로 닫는다

0. **자가 점검**: 이 문서의 해당 구간과 '구간 끝 점검'을 다시 읽고, 빠진 질문이 있으면 저장 전에 묻는다. 사용자가 원치 않아 넘어간 것은 파일의 `진행 기록`에 "건너뜀"으로 적는다
1. **정한 것 요약**: 세 줄 이내
2. **새 결정 기록**: 이번 구간에 추가된 줄을 표로 보여주고 확인받는다
3. **확인 필요 목록**: 무엇을 · 누구에게
4. **솔직한 한마디**: 이 구간에서 가장 불안한 지점 하나
5. **AI가 임의로 채운 칸**: 있으면 목록으로
6. **저장**: 구간 파일과 `{이름}_결정기록.md`를 함께 저장한다. 파일 맨 위에 날짜와 버전을 적는다
7. **이어하기 안내**: 다음 구간 선택지를 2~3개 보여주고 고르게 한다

```
여기까지가 {X}구간이에요. 파일 두 개(구간 파일, 결정 기록)를 드렸어요.
지금 이어가셔도 되고 오늘은 여기서 멈추셔도 돼요.
다음엔 새 대화에 이 파일들을 올리고 "{다음}구간 이어서"라고 하시면 됩니다.

팁: 프로젝트를 하나 만들어 파일들을 넣어두면 매번 올리지 않아도 돼요.
```

## 버전 관리 · 고치기 모드

기획은 여러 날에 걸쳐 고친다. 첫 시안이 나온 뒤로는 구간 순서보다 아래 순서를 따른다.

**보드마다**
- 오른쪽 위에 `v{n} · 최종 수정 YYYY-MM-DD`를 붙인다. 내용이 바뀌어 게시할 때마다 +1. 오탈자·높이 조정만 있으면 같은 날 다음 버전에 묶는다
- 보드 안에서 바뀐 항목에는 `YYYY-MM-DD 변경 / 추가` 표시를 붙이고, 다음 버전이 확정되면 지운다

**페이지 버전 관리 보드**
- 보드마다 한 줄: 보드 이름 · 현재 버전 · 최종 수정 · 이력(버전 · 날짜 · 작성 경로 · 무엇이 바뀌었나)
- **작성 경로**(여러 도구에서 고친다면): `대화`(Claude 대화에서 수정) / `Claude Code`(사용자가 Claude Code로 요청한 수정). 양쪽에서 같은 파일을 고치면 수정 전에 최신 버전부터 읽는다
- 기록이 비어 있는 기간은 '기록 한계'로 솔직하게 적는다

**날짜별 변경 노트**: 고친 날마다 캔버스에 노트 한 장. 누가 정했나 · 새 화면 · 새 결정 번호 · 이름 통일 · 확인 필요(누구에게).

**고치기 순서**
1. 요청이 기존 결정과 어긋나는지 먼저 본다(공통 원칙 7)
2. 이 변경 때문에 같이 바뀌어야 하는 보드 목록을 보여준다. 이름·번호·메뉴·지표처럼 여러 보드에 나오는 것이 바뀌면 특히 빠뜨리지 않는다
3. 사용자가 고르면 보드들을 고치고, 결정 기록 요약 · 페이지 버전 관리 · 날짜별 노트를 **같은 차례에** 갱신한다
4. 고친 보드와 버전 표를 보여준다

## 저장 파일 공통 머리

```
# {이름} — {구간 이름}
| 작성 | {사용자} | 최종 수정 | {날짜} | 버전 | v{n} |

## 정한 것            (결정 번호로 가리킨다)
## 내용               (구간별 본문)
## 확인 필요          (무엇을 · 누구에게)
## AI가 채운 칸 [제안]
## 진행 기록          (날짜 · 한 일 · 건너뛴 질문)
```

문서를 고칠 때는 버전을 올리고 진행 기록에 무엇이 바뀌었는지 한 줄 남긴다. 한 문서에서 이름이나 결정이 바뀌면 **다른 문서에도 같이 반영할지** 묻는다.

## 파일과 시각 자료를 만들 때

- 구조도 묶음 · 화면 시안 · 대시보드 시안 · 결정 기록 요약 · 버전 관리 → Design 캔버스(보드별). 캔버스를 쓸 수 없으면 한 파일짜리 HTML
- 기획서·결정 기록·점검 결과 → 문서 도구나 마크다운 파일
